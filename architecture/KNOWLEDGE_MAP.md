# SYSTEMS

## SYS-01: API Gateway
- **Ответственность**: Единая точка входа для внешних клиентов. Аутентификация, строгая валидация входящих запросов, rate limiting, маршрутизация к внутренним сервисам.
- **Контракты**: REST/JSON (внешние → внутренние), проксирование запросов.
- **Владелец данных**: Не хранит данные.
- **Зависимости**: Conversation Manager, Ingestion Service (через очередь), AuthZ Service.

## SYS-02: Conversation Manager
- **Ответственность**: Оркестрация диалогов с кандидатами. Управление историей, координация поиска и генерации, реализация простых и агентных сценариев. Кэширование готовых ответов по нормализованному запросу.
- **Контракты**: `process_query`, `get_history`, `save_message` (внутренние gRPC/REST).
- **Владелец данных**: История диалогов (PostgreSQL).
- **Зависимости**: Clearing Service, Retrieval Service, Generation Service, AuthZ Service, Translation Service, PostgreSQL, Redis (response cache).

## SYS-03: Retrieval Service
- **Ответственность**: Гибридный поиск релевантных документов (векторный + полнотекстовый). Ранжирование и фильтрация результатов.
- **Контракты**: `search(query, filters, top_k)` → список чанков.
- **Владелец данных**: Векторный индекс (Qdrant), метаданные документов (через Document Storage).
- **Зависимости**: Embedding Service, Qdrant, (опционально) Document Storage.

## SYS-04: Generation Service
- **Ответственность**: Генерация ответов и уточняющих вопросов через LLM (Ollama). Абстрагирует конкретную модель.
- **Контракты**: `generate(prompt)`, `generate_clarification(original_query, documents, history)`.
- **Владелец данных**: Не хранит данные.
- **Зависимости**: Ollama (внешний сервис).

## SYS-05: Embedding Service
- **Ответственность**: Получение векторных представлений текста. Кэширование результатов для ускорения.
- **Контракты**: `embed(text)`, `embed_batch(texts)`.
- **Владелец данных**: Кэш эмбеддингов (Redis).
- **Зависимости**: Ollama, Redis.

## SYS-06: Ingestion Service
- **Ответственность**: Загрузка, чанкинг, индексация документов (резюме). Семантический парсинг резюме с извлечением метаданных (company_name, date_range, project_name, project_domain, role) из иерархической структуры. Поблочный перевод (general + каждая компания отдельно) для предотвращения потери данных при работе с LLM. Версионирование, транзакционная согласованность при обновлении.
- **Контракты**: Принимает команды через очередь (например, `upload_document`), публикует события о завершении индексации.
- **Владелец данных**: Исходные документы, чанки, метаданные (PostgreSQL).
- **Зависимости**: Embedding Service, Translation Service, Qdrant, PostgreSQL, RabbitMQ.

## SYS-15: Translation Service
- **Ответственность**: LLM-перевод текста (через Ollama). Используется при индексации резюме (ru→en). Кэширование результатов в Redis.
- **Контракты**: HTTP `POST /translate` (текст, source_lang, target_lang, опции); очереди `translation_tasks` / `translation_results`.
- **Владелец данных**: Кэш переводов (Redis, отдельная БД).
- **Зависимости**: Ollama, Redis, RabbitMQ.

## SYS-16: Clearing Service
- **Ответственность**: Нормализация входящего текста пользователя (пробелы, технический мусор), валидация (profanity, prompt injection). Используется в FLOW-01 до поиска и генерации.
- **Контракты**: `POST /preprocess` → normalized, validation_result (OK/BLOCK), reasons.
- **Владелец данных**: Не хранит данные.
- **Зависимости**: Нет.

## SYS-17: Telegram Bot
- **Ответственность**: Telegram-интерфейс для кандидатов и HR. Регистрация пользователей, режимы candidate/hr, загрузка резюме, RAG-запросы, match-vacancy. Эскалация: отправка сообщений в телеграм-чат администратора и кандидата по owner_id.
- **Контракты**: API Telegram; вызовы API Gateway (documents/upload, match-vacancy, enqueue).
- **Владелец данных**: users (PostgreSQL, через миграции).
- **Зависимости**: API Gateway, PostgreSQL.

## SYS-07: AuthZ Service
- **Ответственность**: Проверка прав доступа к документам на основе ролей и политик.
- **Контракты**: `check_access(user_id, doc_id, action)`.
- **Владелец данных**: Политики доступа (PostgreSQL).
- **Зависимости**: PostgreSQL.

## SYS-08: RabbitMQ
- **Ответственность**: Инфраструктурный брокер сообщений для асинхронных задач (индексация, обновление кэшей, уведомления).
- **Контракты**: Очереди и обменники, используемые сервисами.
- **Владелец данных**: Временные сообщения (сохраняются при необходимости).
- **Зависимости**: Нет (инфраструктура).

## SYS-09: PostgreSQL
- **Ответственность**: Хранение истории диалогов, исходных документов, политик доступа, users (Telegram Bot), hashes.
- **Контракты**: SQL-доступ через соответствующие сервисы.
- **Владелец данных**: Все данные, перечисленные выше.
- **Зависимости**: Нет.

## SYS-10: Qdrant
- **Ответственность**: Векторное хранилище для поиска по эмбеддингам.
- **Контракты**: GRPC/REST API для записи и поиска векторов.
- **Владелец данных**: Векторные представления чанков.
- **Зависимости**: Нет.

## SYS-11: Redis
- **Ответственность**: Кэш эмбеддингов, временные сессионные данные, кэш готовых RAG-ответов (Conversation Manager).
- **Контракты**: Протокол Redis.
- **Владелец данных**: Кэш.
- **Зависимости**: Нет.

## SYS-12: Prometheus
- **Ответственность**: Сбор и хранение метрик от всех сервисов.
- **Контракты**: HTTP endpoint /metrics.
- **Владелец данных**: Метрики.
- **Зависимости**: Все сервисы, экспортирующие метрики.

## SYS-13: Grafana
- **Ответственность**: Визуализация метрик и логов.
- **Контракты**: Дашборды, подключение к Prometheus и Loki.
- **Владелец данных**: Не хранит.
- **Зависимости**: Prometheus, Loki.

## SYS-14: Loki
- **Ответственность**: Агрегация логов от всех сервисов.
- **Контракты**: Приём логов через драйвер Docker.
- **Владелец данных**: Логи.
- **Зависимости**: Нет.

# FLOWS

## FLOW-01: Query Flow
- **Описание**: Пользователь задаёт вопрос, система (при необходимости) переводит его на английский язык, ищет релевантные документы и генерирует ответ с последующим обратным переводом (если вопрос был задан не на английском).
- **Инициатор**: Пользователь через API Gateway.
- **Участвующие системы**: API Gateway → Conversation Manager → Clearing Service → Translation Service (опционально) → Redis (response cache) → Retrieval Service → Embedding Service → Qdrant → Generation Service → Ollama → PostgreSQL (история).
- **Шаги**:

Препроцессинг и постановка задачи:
1. Запрос поступает в API Gateway.
2. API Gateway создаёт запись диалога в PostgreSQL со структурой:
   - user_raw_text — исходный текст пользователя
   - user_normalized_text — пусто
   - assistant_text — пусто
   - status = queued
   - processing_lock = null
3. Запрос публикуется в RabbitMQ как задача с message_id.
4. Conversation Manager получает задачу и атомарно устанавливает:
   - status = locked
   - processing_lock = worker_id
   -  Если lock установить невозможно — задача отбрасывается как дубликат.

Нормализация и безопасность:
5. Conversation Manager вызывает Clearing Service для нормализации текста:
   - удаление технического мусора
   - нормализация пробелов
   - сохранение семантики
6. Результат сохраняется в user_normalized_text.
7. Clearing Service выполняет security-проверки над нормализованным текстом:
   - profanity
   - prompt injection
8. Если проверка не пройдена:
   - assistant_text = fallback-ответ
   - status = completed
   - processing_lock снимается
   - задача завершается
   - API Gateway возвращает ответ пользователю.

Определение языка и перевод:
9. Conversation Manager выполняет language detection по нормализованному тексту.
10. Если язык ≠ язык генерации:
    - вызывается Translation Service → текст переводится в рабочий язык модели.
11. Переведённый текст сохраняется как working_query.

Кэш ответов:
11a. Поиск в кэше по ключу hash(normalized(working_query)).
11b. При попадании в кэш (cache hit): assistant_text_raw берётся из кэша, переход к шагу 27.
11c. При промахе (cache miss): переход к шагу 12.

Декомпозиция запроса:
12. Conversation Manager определяет, содержит ли запрос несколько подвопросов.
13. Если подвопросов несколько:
    - создаётся внутренняя структура subtask_id для каждого подвопроса.
    - Все подвопросы наследуют message_id.

Обработка подвопросов (выполняется независимо, но под единым lock):
14. Для каждого подвопроса запускается worker.
15. Retrieval Service получает embedding подвопроса (с кэшированием).
16. Производится поиск в векторном хранилище.
16a. Conversation Manager оценивает максимальный score найденных чанков. Если документы не найдены или score < CLARIFY_THRESHOLD: подвопрос помечается failed_retrieval (при необходимости — эскалация). Если CLARIFY_THRESHOLD ≤ score < ANSWER_THRESHOLD — выполняется ветка «Уточняющий диалог» (шаги 16b–16e). Если score ≥ ANSWER_THRESHOLD — переход к шагу 18.
Ветка «Уточняющий диалог»:
16b. Generation Service генерирует уточняющий вопрос (generate_clarification(original_query, documents, history)).
16c. Уточняющий вопрос сохраняется в историю, возвращается пользователю; ожидание ответа в рамках того же диалога.
16d. Получив ответ пользователя, Conversation Manager формирует уточнённый запрос (исходный вопрос + контекст ответа) и повторяет шаги с 15 для уточнённого запроса.
16e. По результатам повторного поиска и генерации — переход к агрегации (шаг 25) или повтор ветки при снова низком score (с лимитом итераций).
17. Если документы не найдены (альтернатива 16a):
    - подвопрос помечается failed_retrieval.
18. Conversation Manager собирает историю диалога.
19. Выполняется token budgeting:
    - сокращение истории
    - суммаризация старых сообщений.
20. Формируется prompt:
    - история + найденные чанки + подвопрос.

Генерация:
21. Generation Service запускает генерацию с retry-лимитом.
22. После каждой генерации выполняется автоматическая проверка:
    - релевантность подвопросу
    - запрещённый контент
    - echo-leak
    - структурная валидность
23. Если проверка провалена:
    - применяется адаптивная стратегия:
    -- изменение температуры
    -- ужесточение prompt
    -- повтор генерации
24. Если лимит retry исчерпан:
    - подвопрос помечается failed_generation.

Агрегация результатов:
25. Conversation Manager собирает результаты подвопросов:
    - если есть успешные ответы:
       -- агрегирует их в единый ответ
    - если все подвопросы failed:
       -- assistant_text = fallback
       -- status = escalated
26. Если часть подвопросов failed:
    - в агрегированный ответ добавляется системное уведомление.

Постобработка и перевод ответа:
27. Если язык пользователя ≠ язык генерации:
    - ответ переводится обратно.
28. Выполняется финальная валидация перевода:
    - семантическое соответствие
    - отсутствие искажений
29. При провале перевода:
    - выполняется повтор перевода с лимитом попыток.
30. Если перевод стабильно провален:
    - статус = escalated.

Кэширование и завершение:
31. Итоговый assistant_text сохраняется в PostgreSQL (assistant_text, assistant_text_translated).
32. Результат кэшируется по ключу hash(working_query) (только при cache miss).
33. status = completed (или escalated при эскалации).
34. processing_lock снимается — _finalize_lifecycle: идемпотентно, crash-safe (release_stale_locks при восстановлении).
35. API Gateway возвращает итоговый ответ пользователю.

Обработка новых входящих сообщений во время выполнения:
36. Если поступает новый запрос до завершения текущего:
    - он получает отдельный message_id
    - не влияет на текущую обработку
    - не изменяет статус активной задачи.

- **Обработка ошибок**:
  - Таймаут или ошибка на любом этапе сетевого запроса → производится retry с экспоненциальной задержкой. Если количество повторных попыток исчерпано, возвращается ответ «Извините, отвечу вам позже.» (на языке вопроса). Диалог эскалируется человеку.
  - Не найдено документов или низкая релевантность → при score в диапазоне [CLARIFY_THRESHOLD, ANSWER_THRESHOLD) выполняется ветка «Уточняющий диалог»; при score < CLARIFY_THRESHOLD — эскалация человеку.
  - Если сервис недоступен, или возникла критическая ошибка, диалог эскалируется человеку.
-  **Логирование событий**:
  - Система логирует ключевые шаги (Loki): время выполнения, ошибки, количество найденных чанков, версии моделей, результаты проверок качества.
-  **Метрики для дашборда**:
  - Процент успешных ответов, доля отфильтрованных запросов, средняя задержка.
  - Счётчики повторных генераций и эскалаций человеку.
-  **Трейсинг**:
  - распределённая трассировка (Grafana Tempo + OpenTelemetry) для отладки узких мест.
-  **Эскалация на человека**
  - При критических ошибках система уведомляет администратора путем отправки сообщения в телеграм-чат с указанием на трассировку.
  - При иных ошибках, требующих эскалации, система пересылает сообщение от рекрутера в телеграм-чат кандидата по `owner_id`. 

## FLOW-02: Ingestion Flow (загрузка резюме)
- **Описание**: Кандидат загружает резюме, система индексирует его и делает доступным для поиска.
- **Инициатор**: Внешняя система или фронтенд через API Gateway.
- **Участвующие системы**: API Gateway → RabbitMQ → Ingestion Service → Translation Service (Ollama) → Embedding Service → Qdrant → PostgreSQL.
- **Шаги**:
  1. Запрос на загрузку с файлом поступает в API Gateway, валидируется и публикуется в очередь RabbitMQ (команда `upload_document`).
  2. Ingestion Service забирает задачу, начинает транзакцию в PostgreSQL.
  3. Удаляет старую версию документа (если есть) и связанные с ней чанки и вектора.
  4. Резюме разделяется на секции (general + experience) через `split_resume_sections`. Experience секция дополнительно разделяется на блоки компаний через `split_experience_by_companies`. Каждый блок (general + каждая компания) переводится параллельно через Translation Service (LLM/Ollama, промпт ru→en из `prompts/translate-ru-en.txt`, до MAX_THREAD_WORKERS одновременно); результаты кэшируются в Redis. После перевода блоки объединяются обратно. Затем сохраняется документ и выполняется семантический чанкинг с извлечением метаданных (company_name, date_range, project_name).
  5. Для каждого чанка вызывается Embedding Service (batch), получаются вектора.
  6. Вектора записываются в Qdrant, чанки и метаданные — в PostgreSQL.
  7. Транзакция фиксируется, публикуется событие об успешной индексации.
  8. (Опционально) Уведомление через callback или WebSocket.
- **Обработка ошибок**:
  - При ошибке на любом шаге транзакция откатывается, сообщение в очереди может быть возвращено для повторной обработки (с ограниченным числом retry).
  - В случае неисправимой ошибки документ помечается как «ошибка индексации» и уведомляется администратор.

## FLOW-03: Match with Vacancy
- **Описание**: HR передаёт описание вакансии и идентификатор выбранного кандидата (owner_id). Система возвращает оценку соответствия кандидата вакансии (relevance_score), сниппеты из резюме и опционально сгенерированный отчёт (плюсы, минусы, итог с числом релевантности). Одновременно выполняется не более одного расчёта (in-process lock).
- **Инициатор**: HR через API Gateway.
- **Участвующие системы**: API Gateway → Conversation Manager → Retrieval Service → Embedding Service → Qdrant; при summary=true — Generation Service → Ollama.
- **Шаги**:
  1. Запрос `POST /match-vacancy` с телом `{ owner_id, vacancy_text, summary: bool }` поступает в API Gateway и проксируется в Conversation Manager.
  2. Conversation Manager захватывает глобальную блокировку (один запрос match-vacancy в момент).
  3. Conversation Manager вызывает Retrieval Service: query=vacancy_text, filters={ owner_id }, top_k=RETRIEVAL_TOP_K.
  4. Для выбранного кандидата (owner_id из запроса) вычисляется relevance_score (среднее по score чанков, 0..1) и matched_snippets — тексты топ чанков по score.
  5. При summary=true вызывается Generation Service: генерируется краткий отчёт (плюсы, минусы, итог с числом релевантности).
  6. Ответ: один элемент `[{ owner_id, relevance_score, matched_snippets, summary? }]` для переданного owner_id; при пустом retrieval или ошибке — `[]`.
- **Обработка ошибок**: ошибка retrieval или генерации → возврат `[]` (без падения); блокировка снимается по завершении обработки.

# CLIENT INTEGRATION (Frontend / внешние клиенты)

- **Базовый URL API (локально)**: `http://localhost:8001` (порт api-gateway на хосте, см. docker-compose `8001:8000`).
- **Загрузка резюме (FLOW-02)**: `POST http://localhost:8001/documents/upload` (multipart: `file`, `owner_id`, опционально `external_id`). Статус задачи: `GET http://localhost:8001/documents/tasks/{task_id}/status`.
- **Соответствие вакансии (FLOW-03)**: `POST http://localhost:8001/match-vacancy` body `{ owner_id, vacancy_text, summary: bool }` → `[ { owner_id, relevance_score, matched_snippets, summary? } ]`.
- **CORS**: В api-gateway задаётся через `CORS_ORIGINS` (список origins через запятую). Если не задано или `*` — разрешены все origins без credentials.
- **Ошибка "Failed to fetch / URL scheme must be http or https"**: Возникает в браузере, когда в `fetch()` передаётся не http(s)-URL (пустая строка, `undefined`, или страница открыта по `file://`). **Решение**: во фронтенде задать базовый URL API явно (например `VITE_API_URL` или `NEXT_PUBLIC_API_URL` = `http://localhost:8001`) и не вызывать fetch при пустом/отсутствующем значении.

# ARCHITECTURAL NOTES

* Index describes architecture, not implementation.
* Modules are capability boundaries.
* Flows describe behavior paths.
- **Независимость систем**: каждый сервис имеет собственное хранилище данных и может масштабироваться независимо.
- **Асинхронность по умолчанию**: для длительных операций (индексация, уведомления) используется RabbitMQ.
- **Жёсткая валидация на входе**: все запросы к API Gateway проходят проверку по Pydantic-схемам.
- **Сквозной trace_id**: все внутренние вызовы содержат заголовок X-Request-ID для трассировки. В логах по каждому шагу цепочки пишется структурированная строка: trace_id, service, operation, target_service, target_resource (таблица/коллекция/очередь/модель). Контракт: CTR-29; реализация: shared/tracing.py, сборка через Dockerfile.service.
- **Безопасность**: все документы считаются персональными данными, доступ к ним контролируется через AuthZ Service.
- **Семантический парсинг резюме**: Ingestion Service использует иерархический парсер (`semantic_resume`) для извлечения структурированных метаданных из резюме. Поддерживаются метки: `Company:`, `Period:`, `Project Name:` (название проекта), `Project Subject Area:` / `Project Area:` / `Project Domain:` (предметная область проекта), `Position:` / `Role:` (должность, применяется ко всем проектам компании), `Responsibilities and Achievements:`, `Technologies Used:`. Парсер распознает как одно-проектные, так и мульти-проектные структуры компаний. Метаданные (company_name, date_range, project_name, project_domain, role) сохраняются в payload векторов Qdrant и в chunks.metadata PostgreSQL для фильтрации и ранжирования при поиске.
- **Поблочный перевод**: для предотвращения потери данных при работе с LLM (ограничения контекстного окна, обрезание длинных текстов) резюме переводится по блокам: general секция + каждая компания отдельно. Блоки переводятся параллельно (до MAX_THREAD_WORKERS), затем объединяются обратно. Каждый блок кэшируется в Redis независимо.
- **Технологический стек**: Python 3.11+, Ollama (локально), Docker Compose, PostgreSQL, Qdrant, Redis, RabbitMQ, Prometheus/Grafana/Loki.
